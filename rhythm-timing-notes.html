Browser rhythm games: BPM, subdivisions, and input windows

Timing code becomes easier to debug when a game converts BPM to milliseconds once, then compares input timestamps against a separate judgement window. Rendering, audio scheduling, and scoring can share the same normalized clock.

Normalize the beat

function timingFromBpm(bpm, subdivision = 4) {
  const safeBpm = Math.min(400, Math.max(20, Number(bpm)));
  const beatMs = 60000 / safeBpm;
  return {
    beatMs,
    subdivisionMs: beatMs / Math.max(1, Number(subdivision))
  };
}

function judgement(deltaMs, windowMs = 45) {
  const delta = Math.abs(Number(deltaMs));
  if (delta <= windowMs) return "perfect";
  if (delta <= windowMs * 2) return "good";
  return "miss";
}

Keep the clocks separate

  • Use an audio or monotonic clock for hit timing, not a frame counter.
  • Apply input latency calibration before scoring.
  • Keep the note subdivision separate from the visual animation step.
  • Clamp impossible BPM values at the input boundary.

Useful test cases

At 120 BPM a beat is 500 ms and a sixteenth note is 125 ms. Test an input exactly on the boundary, just outside it, and a long-frame scenario where rendering misses a frame. These cases expose rounding and timer drift.
